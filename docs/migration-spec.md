# Firebase 이관 요구사항

## Must

- 기존 사용자가 동일한 이름·비밀번호로 로그인할 때, 웹은 동일한 학생과 배정 단어장을 표시해야 한다.
- 로그인 실패 시 웹은 기존 실패 동작을 유지해야 한다.
- 학생이 기존 숙제·오답·기록을 열 때, 이전 전후의 기록과 완료 판정은 동일해야 한다.
- 선생님이 학생·단어장·숙제·기록·공지·시상을 관리할 때, 기존 기능과 집계 의미를 보존해야 한다.
- 학부모가 이미 받은 링크 또는 설치한 웹앱을 열 때, 동일한 자녀 정보에 접근할 수 있어야 한다.
- 웹 푸시가 발생할 때, 기존 학생·학부모 서비스워커 경로를 함께 지원해야 한다.
- 이전 작업을 재실행할 때, 같은 원본 행이 중복 생성되지 않아야 한다.
- 전환 중 쓰기가 발생할 때, 결과는 단일 권위 저장소에 기록되고 누락·중복 여부를 검증할 수 있어야 한다.
- 실패로 복구할 때, 전환 이후 발생한 쓰기를 보존한 뒤 기존 경로로 복구할 수 있어야 한다.

## Should / Could / Won't

- Should: 화면/비즈니스 로직보다 공통 API 경계에서 백엔드를 교체한다.
- Could: 읽기 결과를 별도 환경에서 대조하는 도구를 추가한다. 운영 쓰기 이중 실행은 하지 않는다.
- Won't (이번 단계): RN 구현, 새 PIN 정책, UI 개편, 새 학습 기능, 운영 데이터 삭제. 검증 후 원본 저장소 배포와 비공개 복제는 포함한다.

## 수용 기준

| Given | When | Then |
|---|---|---|
| 기존 학생 계정 및 배정 | 기존 자격증명으로 로그인 | 같은 학생·배정 반환, 재가입 불필요 |
| 같은 기록 스냅샷 | 두 백엔드에서 숙제/오답/점수 조회 | 정규화된 값·완료 판정·집계가 일치 |
| 이미 배포한 학부모 링크 | 새 백엔드에서 열기 | 같은 자녀, 기존 링크 유지 |
| 네트워크 실패 또는 재시도 | 시험 결과 전송 재시도 | 제출 ID 기준 한 건만 반영 |
| 기존 페이지를 열어둔 클라이언트 | 전환 시점 이후 제출 | 정의된 단일 쓰기 경로에 반영 |
| 전환 이후 새 기록 존재 | 롤백 리허설 | 새 기록 보존 후 기존 백엔드에서 조회 가능 |

## 비기능 요건과 검증

기존 출력·PIN·메모·시간대를 보존하고 오류 시 다른 원장에 자동으로 쓰지 않는다. 표 단위 모델은 현재 소규모 사용 범위에 맞추며 무료 할당량과 문서 크기를 관리한다. 실제 동시 쓰기/충돌/중복 시험/PIN 변경/링크 폐기/그림 실패/푸시 위임/전환 freeze는 Emulator에서 검증한다. 원본 운영 쓰기를 시험 삼아 발생시키지 않는다.

운영 v80와 중간/최종 snapshot, 새 Firebase 서울 프로젝트가 확보됐다. 최종 셀/메모 전체 대조, 실제 SDK와 기존 GAS 출력 대조, 복구 리허설, 브라우저 및 배포 검증 결과는 docs/gate-reviews.md에 기록한다. 예약 트리거는 소유 계정별 목록이므로 현재 계정 UI의 0개를 전체 프로젝트에 트리거가 없다는 증거로 해석하지 않는다.

## 추가 요청: 서비스 분리와 정교한 검증

사용자가 기존 요청 처리를 서비스 파일로 통합하고 이전 전후 테스트를 강화하도록 요청했다. 기존 `api(fn, ...args)` 호출자 계약을 유지하고, HTTP 전송/응답 봉투 해석은 한 소스 파일이 소유한다. GitHub Pages, Apps Script 내부 실행, 로컬 미리보기, 두 서비스워커를 모두 지원한다. 리팩터링 단계에서는 백엔드 전환이나 로그인 정책 변경을 섞지 않는다.

새 Firebase 프로젝트 생성은 승인되었다. 계정 인증/소유 계정 확인 전에는 프로젝트를 임의 계정에 만들지 않는다.
